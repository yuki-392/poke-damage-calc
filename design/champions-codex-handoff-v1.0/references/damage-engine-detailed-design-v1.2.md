## 0. 決定事項と根拠のレベル

この設計文書は、次を区別する。

- **確定（ユーザー要求）**: 共通計算エンジン、最大4技×50匹、能力ポイント、詳細内の戦闘条件は一時値、未対応効果を正確として表示しないことなど。
- **設計決定（実装契約）**: 入出力モデル、フェーズ、効果レジストリ、実行トレース、エラー種別、テストの合格条件。
- **暫定仮説（調査中）**: Championsでの一部技・特性・持ち物の利用可否、実際の補正順と端数処理、メガシンカの効果、乱数仕様の実機一致。未検証の仮説を「確定」としない。

参照したWikiはChampions専用ドメインに存在するが、テラスタル・ダイマックス・Z技など複数作品の記述が混在する。このページはルール実装の**候補資料**であって、現行Championsにおける全効果の存在・補正を保証しない。

主な参照:
- https://champions.pokewiki.net/ダメージ計算式 （補正手順・4096固定小数・丸め・乱数）
- https://www.pokemonchampions.jp/ja/ （Champions公式）
- `/mnt/data/champions-damage-engine-v1.1/docs/implementation-v1.1.md` （既存試作の実装範囲）
- `/mnt/data/screen-design-v0.5.md` （確定UI）

## 1. スコープと非スコープ

### 1.1 このエンジンが返すもの

1. 単発の攻撃が命中した場合のダメージ確率分布（同一ダメージ値の重みを含む）。
2. 最大HPを分母とする最小～最大の与ダメージ割合、攻撃後の残HP範囲。
3. **同じ条件の攻撃が独立に繰り返され、ターンの途中・終了にHP回復や能力変化がない**前提での確定数と撃破確率。
4. 計算に適用した効果と、効果の発動を阻止した要因のトレース。
5. 計算不能な場合、`unsupported`/`missingContext`/`invalid`などの構造化された原因。

### 1.2 ここで自動的には扱わないもの

- 技の命中率・急所**発生率**・追加効果発生率を、単純なダメージ乱数による撃破確率に混ぜない。
- みがわり、交代、行動順による場の状態変化、毎ターン回復、状態異常による継続ダメージなどの多ターン戦闘シミュレーションは**独立機能**とし、対応時まで上記の限定条件を表示する。
- 特殊な技の「追加効果の○%」は技マスターデータの**表示属性**。追加効果そのものをダメージ分布へ混ぜるかは効果ごとに明示的に設計する。
- 習得可否とダメージ計算可否は別判定。UI要件どおり、習得外の**存在する技**を手入力して計算できるが、使用可能なゲーム技かつ効果実装済みであることが必要。

## 2. モジュール境界（責任分担）

| モジュール | 責任 | 禁止事項 |
|---|---|---|
| `data-resolver` | Pokémon/フォルム/技/特性/持ち物の**バージョン付きマスター**を引く | 画面から受け取った日本語表示名を直接ID扱いしない |
| `ruleset` | レギュレーション別の使用可否、計算ルール・補正順、適用効果版を決定 | 他作品のルールを黙って流用しない |
| `context-resolver` | 実際の接地・天候有効性・相手特性無効化・持ち物有効性・対象数などを評価 | 情報不足を勝手にfalseとみなさない |
| `stat-resolver` | 6能力の実数値、能力ポイント配分、ランク、急所によるランク無視 | UIで非表示の能力をゼロにすること |
| `move-resolver` | 技タイプ・分類・威力・攻防参照・命中対象の動的決定 | 未分類の技を通常威力技にフォールバックすること |
| `effect-engine` | 技・特性・持ち物・場の条件の発動可否、処理順、重ね掛け | 発動順不明の倍率を最終ダメージにまとめること |
| `damage-core` | 基礎ダメージ、順序付き固定小数、16乱数または特殊分布 | 浮動小数計算を無検証で混ぜること |
| `ko-analyzer` | 分布から確定数・撃破確率を得る | 命中・追加効果込みの確率と混同すること |
| `top50-adapter` | 1～4技×50匹を同じコアへ変換 | TOP50専用の異なるダメージ計算式を持つこと |
| `ui-adapter` | Japaneseの表示文字列・HPバー・エラー説明 | 計算結果の数値を独自に再計算すること |

## 3. 入力契約：厳密な概念モデル

`calculateDamage(request, ruleCatalog, masterCatalog) -> DamageResult` は副作用のない決定的関数とする。同じ入力・同じルール・同じマスターで出力は必ず同じ。

### `DamageRequest` に最低限必要な情報

- `rulesetId`（Champions）・`regulationId`・`ruleVersion`・`masterDataVersion`
- 攻撃側／防御側：`pokemonFormId`, 全6能力ポイント配分、性格補正の**全5能力**、現在HP、能力ランク、状態異常、特性ID、持ち物ID、メガ形態／条件
- 技：`moveId`（マスター参照。タイプ・威力は**マスターを優先**し、実際に変化する場合は動的解決）
- 対戦形式、天候、フィールド、壁、急所に当たったか、実際の攻撃対象数、接地状態、持ち物・特性の有効性の入力／導出条件
- 味方支援・防御側の味方特性・行動順・技に必要な相手/味方の残HP等を含む**条件付き文脈**

既存v1.1の`moveSpecificConditions: Record<string, boolean|number|string>`は試作用。**本番契約では型付き discriminated union のコンテキスト**へ置換する。表記揺れの文字列で効果判定しない。不要な条件まで毎回入力を要求せず、技・効果が必要とするキーだけ要求する。

### 状態の区別

- `ok`: 該当条件の効果をすべて解決済み。確率分布付き。
- `nonDamaging`: 変化技等、直接ダメージを扱わない技。例外的に反動/固定HP変化がある場合の扱いは技定義で分ける。
- `missingContext`: 計算ルールは実装済みだが、発動条件を決める値が不足。例：ジャイロボールで対象素早さが未設定。
- `unsupported`: 効果自体またはChampions固有の挙動が未実装・未検証、あるいは利用できるマスターがない。
- `invalid`: ポイント上限超過、実数値の逆算不可、技・特性のIDが非法、矛盾する持ち物など。

UIの簡潔さのため、`missingContext` と `unsupported` はともに「この条件では計算できません」と表示できるが、内部コードとユーザーへの修正方法は必ず区別する。v1.1にない新状態として設計時に追加する。

### エラーの機械可読仕様

`{status, code, fieldPaths, missingKeys, messageKey, ruleVersion, sourceIds}`。`messageKey`から日本語文言を生成。**絶対に不完全な数値を `ok` と同時に返さない**。

## 4. Champions固有の能力ポイントとUI

- Lv50固定、HP=`B + 75 + P`、その他=`floor((B+20+P) × natureFactor)`。6能力のポイントは整数・各0～32・合計0～66。
- 目に見える欄：攻撃側は物理なら攻撃／特殊なら特攻、防御側はHP＋防御または特防。ただし**データは全6能力分保持**する。
- 実数値を入力すると0～32を全探索し、既存の他能力の配分を保持しながら一意に選ぶ。候補が複数あれば「前の値に近い→小さいP」の優先順位。該当なし/上限超過ならUIポイント=`?`・エンジン`invalid`。
- 攻撃側の素早さやHP、防御側の攻撃など、**特殊な技が非表示の能力を参照する場合**は文脈不足かどうかを判断し、対象能力を一時的に表示するか取り込み済み値を使用する。未入力を暗黙で0にしない。
- 性格欄はUIで `0.9/1.0/1.1`。内部では性格名が由来の全能力補正を保存し、実測・推定型の情報を壊さない。
- 特殊HP種族（HPが1固定等）・特定フォルムの計算は、専用のルールIDと照合済みフィクスチャが必要。

## 5. ダメージ計算のパイプライン

`Prevalidate -> Resolve Forms & Effects -> Resolve Dynamic Move -> Immunity/Suppression -> Final Power -> Final Attack -> Final Defense -> BaseDamage -> Ordered Modifiers -> Outcome Distribution -> KO -> Trace`

以下は**参照Wikiに記載された処理例**を移した実装順序の候補。ゲーム内テストで確定させる。補正の端数は `4096=1.0` として**フェーズごとの** `floor` / `round-half-up`（四捨五入） / `round-half-down`（五捨五超入）を明示する。JSの`Math.round`等に一任しない。

| 位置 | 処理 | 例 | 丸め |
|---|---|---|---|
| M0 | 技の動的基礎威力とタイプ・分類を確定 | アクロバット、テラ由来の技変化が存在するなら別定義 | 効果固有 |
| P1 | 技威力補正値の合成 | テクニシャン、てだすけ、タイプ強化道具 | 4096基準／合成時四捨五入候補 |
| P2 | 最終技威力 | `basePower × powerModifier` | 五捨五超入候補 |
| A1 | 攻撃側の対象能力決定、ランク・効果 | ちからもち、こだわりハチマキ | 能力ランク切り捨て、効果は対象フェーズで処理 |
| D1 | 防御側の対象能力決定、ランク・効果 | しんかのきせき、砂・雪 | 能力ランク切り捨て、効果は対象フェーズで処理 |
| B1 | 基礎ダメージ | `floor(floor(22*power*attack/defense)/50)+2` | 切り捨て |
| F1 | 複数対象補正／天候／急所 | 0.75, 0.5/1.5, 1.5 | 五捨五超入候補 |
| F2 | 乱数 | 85,86,...,100 /100 | 切り捨て |
| F3 | タイプ一致→相性→やけど | 1.5、0/0.5/2、0.5 | 一致とやけど：五捨五超入候補／相性：切り捨て |
| F4 | ダメージ補正値合成 | 壁、いのちのたま、フィルター等 | 合成時四捨五入、最終適用は五捨五超入候補 |
| F5 | 最小1・無効化例外 | 0相性・特性無効は0 | 特殊ルール |

**二重適用を防ぐ**: 効果定義には必ずただ1つの主適用フェーズを割り当てる。例：てだすけを「威力補正」と「最終倍率」の双方へ登録しない。ダブルの範囲技補正も`F1`のみ。

**発動阻害を先に判定**: 型無効、特性による吸収/無効/タイプ変更、天候の無効化、かたやぶり系の特性無効化、持ち物無効化、接地判定、急所による壁無視を先に解決する。処理順が相互依存する場合、明示的なルールで調停し、循環・未定義の優先順位は`unsupported`。

### 丸めの数値例

ダメージの基本式で `Lv50、威力100、攻撃182、防御189` は補正前ダメージ44。85～100の乱数適用後16候補は `[37,37,38,38,39,39,40,40,40,41,41,42,42,43,43,44]`。これは計算基礎の**固定フィクスチャ候補**。他の補正が重なるケースはゲーム内照合で期待値を確定させる。

## 6. 特殊効果の処理設計

### 6.1 効果レジストリ

マスターデータには `effectIds[]` を宣言し、`effects-catalog-v1.2.csv` の効果定義と**一対一または明示された複数ID**で結びつける。効果定義は以下を持つ。

- `effectId`, `category`（技/特性/持ち物/場）, `phase`, `requiredContext`, `trigger`, `suppressions`, `ruleVersionRange`, `verificationStatus`, `fixtureIds`。
- `ruleVersionRange`に入っても、レギュレーションで技・特性・持ち物が未解禁なら使用不可として扱う。**Wiki掲載 = Champions実装済み** とみなさない。
- `verificationStatus`: `verified_in_game`, `secondary_source_only`, `spec_pending`, `not_applicable`。試作実装済みという状態は**別列**で追跡する。
- 対戦に存在する全ての技・特性・持ち物IDが `implemented` / `audited_neutral` / `conditional_context` / `unsupported` / `not_applicable` のいずれかへ**漏れなく分類**されることを本番公開ゲートとする。

### 6.2 技カテゴリ

| 種類 | 代表例（※Champions収録可否は別判定） | 必要な追加文脈 | ポリシー |
|---|---|---|---|
| 標準の物理・特殊 | じしん、10まんボルト | 対象数、タイプなど | 通常の計算パイプライン |
| 動的威力 | しおみず、からげんき、アクロバット、ベノムショック | 相手HP割合、状態異常、持ち物有無など | 威力確定後に標準パイプライン |
| 素早さ・重量・能力を参照 | ジャイロボール、くさむすび、ボディプレス | 攻守の素早さ、重量、防御値等 | 必要能力を要求し、参照能力を明示 |
| 残HPに比例 | ふんか、しおふき | 攻撃側現在HP/最大HP | 威力の上下限・丸めを個別に定義 |
| HP割合・固定ダメージ | いかりのまえば、ちきゅうなげ、固定値効果 | 対象HP、レベル | 固有のダメージ分布モデル |
| 連続技 | ロックブラスト、スケイルショット | ヒット数分布、各ヒットの効果 | 畳み込み／相関を個別に解決 |
| 攻防を特殊に参照 | サイコショック、イカサマ | 防御側の攻撃など | 計算時の参照能力を上書き |
| 状況によりタイプや範囲が変化 | ウェザーボール、ワイドフォース | 天候／フィールド／接地／対象数 | 技データの解決段階に処理 |
| ダメージを与えない変化技 | まもる等 | — | `nonDamaging`、ダメージ0と混同しない |

**特殊な技に万能な「任意倍率」欄を提供しない。** 発動条件の不明なものは`missingContext`で止める。使える技一覧・レギュレーションとの照合を終えたものから効果登録する。

### 6.3 特性カテゴリ

- 威力補正: テクニシャン、かたいツメ、がんじょうあご、きれあじなど。**適用技タグ**（接触/かみつき/斬撃等）を必要とする。
- 攻撃能力補正: ちからもち、ヨガパワー、こんじょう、サンパワーなど。効果発動条件や参照能力を定義。
- 防御能力補正: ファーコート、ふしぎなうろこなど。技分類・状態異常が必要。
- 被ダメージ補正: マルチスケイル、フィルター、フレンドガードなど。HPが満タンか・相性・味方が存在するかなどが必要。
- 無効/吸収/タイプ変更: ふゆう、ちくでん、もらいび等。**ダメージ倍率より前**に評価し、結果0/回復/強化などを区別。
- 効果阻害: かたやぶり系など。攻撃側・防御側の特性間の相互作用を先に解決し、後段の判定へ反映。
- 明示的に計算に影響しない特性: 状況を確認して`audited_neutral`へ登録。単に未知の特性名だから無影響扱いすることは禁止。

### 6.4 持ち物カテゴリ

- 技威力: タイプ強化アイテム、ちからのハチマキ、ものしりメガネなど。
- 攻防能力: こだわりハチマキ/メガネ、しんかのきせき、とつげきチョッキなど。
- 最終ダメージ: いのちのたま、たつじんのおび、半減きのみなど。
- 発動条件の変化: たべのこし、きのみ、消費済みかどうか、技を受ける前後の発動タイミング。
- メガストーン: フォルム変更・持ち物の制限は`form-resolver`で検証し、通常アイテム補正を別途掛けない。
- 任意の文字入力: UIで許可。ただし**未登録文字列を『効果なし』として扱わない**。解決不能なら`unsupported`、持ち物「なし」は明示ID `none`。

### 6.5 ダブル

- UIは攻撃側1匹・防御側1匹を維持する。技のターゲットタグと、実際にダメージを受ける対象数を別に保持する。
- てだすけ、壁、味方のフレンドガードなどは**抽象化した補助条件**で入力可能とする。
- 「ダブル」だけで範囲補正は付かない。2体以上へ同時命中した場合に適用する。
- 味方や相手の特性を複数指定したとき、どの効果が掛かるか・同じ特性が重なるかは効果レジストリで定義する。**推測で単純積算しない**。

## 7. KO確率の契約

- 基本ケース: 16等確率ダメージ `rolls[]`。同じダメージ値でも重みは統合せず保存、または重み付き確率質量関数として正確に管理する。
- `minDamage>0`なら `最速撃破可能数=ceil(currentHp/maxDamage)`、`確定撃破数=ceil(currentHp/minDamage)`。
- これらが同一なら `確定n発`。異なれば最速撃破可能数`n`に対して**そのn回で撃破する確率**を厳密な分数（BigInt等）で計算し、`乱数n発(XX.X%)`と表示する。
- **3発以上でも正しい整数nを表示**。例 `乱数5発(13.6%)`。TOP50の「3発以上」フィルタはUIの絞り込みのみ。
- 常に0ダメージの場合は `無効` または `この条件では撃破不可`。ダメージの最大値はあるが最小値が0（技固有乱数など）では**確定数が無限**のケースを表現する。
- 連続技は独立/相関/ヒット数分布を効果モデルで宣言し、単発16乱数を無条件で掛け合わせない。
- 確率表示の小数1桁は**表示フォーマッタのみ**で処理。要件サンプル `56.2%` と数学的四捨五入した `9/16=56.3%` の差は、実装時にUIポリシーを固定する（本設計は四捨五入を採用候補）。

## 8. UI v0.5との接続条件

- エンジンは`type/status/resultCode`を返す。表示文言はUI側で作成。
- 4技が物理/特殊混合なら、攻撃側の攻撃/特攻、防御側の防御/特防を**技ごとに参照**する。非表示能力値は保持する。
- 通常計算の攻守交換後は、攻撃側・防御側の状態と設定の由来を保ち、技の合法候補を再表示する。
- TOP50詳細の一時変更：技・戦闘条件は閉じると破棄。型の変更だけ該当するTOP50個体へ保持。詳細から通常計算への遷移時は**一時条件も含めて**スナップショットとして渡す。
- 一覧のHPバーは最大HPではなく**残HPの比率**で描き、右端から減る。バーに与ダメージ割合を必ず併記。色の閾値は画面設計v0.5を参照。
- エラーや未対応は50件全体を落とさず、対象となる技×個体のセルだけに理由を表示。

## 9. 非機能・トレーサビリティ

- バージョン: `ruleVersion`, `masterDataVersion`, `regulationId`, `effectCatalogVersion` をリクエスト・結果・保存/共有スナップショットに保持。
- ロギング: `effectId`, `trigger`, `phase`, `before`, `modifier4096`, `roundingMode`, `after`, `sourceId`, `wasSuppressed`, `reason`を結果トレースに含める（機密情報・保存アカウント情報を含めない）。
- 再現性: 同入力同版で同出力。レギュレーション変更時は**以前の計算を静かに新ルールで再計算しない**。
- 性能: 200組の算出＋描画がデータ読み込み後3秒以内を暫定目標。重い連続技計算は重み付き分布の効率化、必要に応じてWeb Worker。
- 入力検証: 最大ポイント66、各能力0–32、HP上限、能力ランク -6..+6、使用可能技/特性/持ち物のレギュレーション判定（**習得外の技は計算上許容**）。

## 10. 受け入れ基準（設計段階で定義）

| ID | 必要な試験 | 完了条件 |
|---|---|---|

## 11. 設計上の未確定事項・判断ゲート

| 優先 | 未確定項目 | 必要な確認 | Codex実装時の安全動作 |
|---|---|---|---|
| P0 | 現行Championsの16乱数と完全一致するか | 実機・実測値比較 | 旧仕様を確定済みと記載しない |
| P0 | 複数効果の適用順と丸め | 補正重複ケースのゴールデンテスト | 未検証効果を`unsupported`にする |
| P0 | 技・特性・持ち物の現行収録状況 | バージョン付き公式/信頼できるデータ | 未登録のIDに勝手な通常効果を割り当てない |
| P0 | メガのフォーム・必要アイテム・能力参照 | フォルムマスターと実機照合 | 未確認は`unsupported` |
| P1 | 効果阻害・特性無効化の相互作用 | 代表組合せで検証 | 競合を解決できない場合 `unsupported` |
| P1 | 連続技の乱数相関・途中の持ち物消費 | 連続技ごとの実機比較 | 汎用16乱数を流用しない |
| P1 | 毎ターン回復/天候ダメージを撃破確率へ含めるか | ユーザー要件の追加決定 | 現状は含めず注記 |
| P2 | 追加効果がダメージ自体へ影響する特殊例 | 技一覧・効果IDの全件監査 | 表示属性と計算効果を区別 |

このリストがゼロにならなければ設計完了できないわけではないが、**P0は本番実装の完成条件**に据える。
